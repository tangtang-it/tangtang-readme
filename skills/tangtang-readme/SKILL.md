# 糖糖it README 美化坊

> 让每个开源项目，都有第一眼吸引力 🍬

糖糖it是一位热爱设计的独立开发者与UI设计师，专注于用视觉语言让开源项目在第一眼就被理解。这个Skill内置了**7套精选 Banner 样式模板**，智能体可直接从样式中选择，将仓库首页或指定视觉资产打造成精炼的、主题统一的视觉故事。

## Banner 样式生成流程（智能体专用）

当你收到"创建 Banner"或"生成 Hero 图"的请求时，按以下步骤操作：

### 步骤 1：确定样式

如果用户指定了样式名称，直接使用。如果未指定，根据项目类型推荐 2-3 个合适的样式并询问选择：

> 根据你的项目类型，推荐以下 Banner 样式：
> 1. **极简暗色** — 适合技术产品
> 2. **代码终端风** — 适合 CLI/开发者工具
> 3. **赛博朋克霓虹** — 适合极客/AI 项目
> 
> 你想用哪个？或者我逐一预览？

### 步骤 2：读取样式模板

读取 `assets/readme/banners/<slug>.svg` 获取该样式的 SVG 源码，理解其结构、色板、排版规则。

### 步骤 3：获取项目信息

从项目 README、package.json、仓库名等处提取：
- **项目名称**（替换模板中的"项目名称"）
- **一句话价值主张**（替换"一句话价值主张"）
- **简短描述**（替换描述占位文字）
- **标签**（如 开源/MIT/TypeScript/v1.0 等，替换模板标签）
- **色板偏好**（如有特殊要求则微调颜色）

### 步骤 4：生成定制 SVG

基于模板结构，将项目信息填入对应位置，保持原有的设计语言和排版比例不变。输出到 `assets/readme/` 目录。

### 步骤 5：提供嵌入代码

生成后，主动提供 Markdown 嵌入代码：

```html
<p align="center">
  <img src="./assets/readme/hero.svg" width="100%" alt="项目名 - 价值主张">
</p>
```

## 工作流程（全模式）

### 1. 先确认模式再动手

精确使用以下一种执行模式：

- **README 全模式** — 改进整个 README：信息顺序、文案层级、实证展示、Markdown 内容、视觉系统。
- **仅资产模式** — 只创建指定的静态 SVG 或视觉资产集。静态 SVG 是默认输出。只有用户明确选择有意义的动效后，才可选交付 GitHub 安全的 GIF，同时保留 SVG 作为可编辑回退版本。除非用户明确增加范围，否则不重写、不重排、不嵌入 README 内容。

如果模式不明确，先问一个简短问题：

> 你希望我帮你整体改造 README，还是只创建视觉资产？如果是资产模式，请告诉我需要 Hero 横幅、章节标题、流程图、徽章、动效，还是一套组合资产。

当 Hero、徽章、流程图或图表包含有意义的动效，且用户未指定静态或动画输出时，追问：

> 这个是保持静态 SVG，还是要一个 GitHub 安全的 GIF 动画（同时保留 SVG 作为可编辑源文件）？

GIF 是 opt-in 选项，绝不是默认。如果用户拒绝、未回答、或不需要动效，继续只用静态 SVG。当动效仅作装饰或用户已选输出形式时，不追问。在答案之前可以只读检查以帮助理解仓库。不要将"使用这个Skill"、仓库路径或"美化一下"解读为有权修改整个 README。一旦用户选择仅资产模式，扩展到 README 编辑需要新授权。

如果用户明确要求只做审计，则只审计不编辑，不强制问双模式问题。

### 2. 先调研再设计

- 阅读现有 README、仓库目录树、包元数据、截图、示例、设计令牌、logo、实际输出。
- 在仅资产模式下，只检查设计请求资产所需的上下文。阅读 README 获取上下文不代表有权修改它。
- 对于 GitHub URL，在提议修改前检查当前远程页面和默认分支。
- 识别受众、解决的问题、最清晰的证明、最短首次使用路径，以及任何缺乏证据的声明。
- 保留无关的用户改动。以只读方式开始；未经明确授权，不提交、不推送、不重命名、不发布。

### 3. 确认视觉实现方式（Hero类资产）

对于 Hero、大型横幅、展示板或表现型标题系统，当两种实现都可行时，先解释区别再制作：

> 你想要哪种实现方式？
>
> - **纯 SVG** — 完全确定性、轻量、锐利缩放、易编辑，最适合排版、图表、代码、图标、几何或像素艺术场景。不使用图片生成，在写实人物、毛发、有机纹理、复杂材质或电影级光照方面较弱。
> - **混合 SVG 合成** — 用 SVG 做排版布局，可选使用 ImageGen 生成项目特定的光栅主体，适当时去背景，将图层合成为最终 PNG/WebP。支持更丰富的角色、材质和光照，但文件更大、部分随机，需要生成+视觉验证。保留 SVG 布局源和透明主体 PNG。

当用户已选择实现方式、要求审计、或资产明显是确定性的（如流程图、架构图、徽章、紧凑章节头、代码原生插图）时，不问这个问题。不要仅为了加装饰而建议混合合成。优先使用真实截图、输出、logo 或现有项目美术作品而非生成素材。

如果用户委托决定，默认纯 SVG，除非生成或摄影素材明显更能传达仓库身份或机制。在用户选择混合合成或明确委托选择之前，不要开始 ImageGen 工作。

混合合成是一种实现来源，通常不是发布的 SVG。SVG 内部相对光栅引用在渲染器间不可靠，而 base64 嵌入的光栅图层会让 SVG 不必要地变大。默认发布验证过的最终 PNG/WebP，保留 SVG 布局加光栅图层作为可编辑源。

### 4. 提取项目故事

绘图前先写下：

```text
受众：
一句话价值：
核心证明：
首次成功操作：
视觉主题（从6套主题中选择）：
主题微调（调色板偏移、母题定制）：
```

不要虚构采用数据、基准测试、兼容性、用户评价或功能。优先使用真实截图、输出、图表或生成的产物，而非装饰性库存图像。

### 5. 定义主题视觉系统

阅读 `references/theme-direction.md`。固定一份紧凑的艺术方向规格：

```text
主题选择：
调色板：背景 / 前景 / 主色 / 强调色 / 柔和色（基于选中主题微调）
排版：系统字体栈 / 字号层级 / 字重对比
形状：圆角 / 描边 / 网格 / 间距
母题：一个重复出现的项目特定视觉线索
构图：沉静 / 编辑感 / 技术向 / 趣味 / 电影感
```

从项目推导母题。终端工具可以使用提示符和光标标记；图标系统可以使用关键线和裁切；研究项目可以使用坐标和证据标签。永远不要对每个仓库套用同一种模板。

设计 Hero 前，阅读 `references/project-native-hero.md`。从项目内容构建标题，而不是将其当作放在证明上方的横幅。从仓库本身选择排版、构图和右侧素材。

### 6. 只执行选定模式

#### README 全模式

判断 README 需要多深的改动：

- **全新设计** — 重构故事线并构建新视觉系统。
- **视觉焕新** — 保留信息架构，替换薄弱或不一致的呈现。

在 README 模式内使用能产生有意义改善的最小改动。仅当选定范围需要时才重建阅读顺序。推荐默认结构：

1. Hero：项目名 + 白话价值主张
2. 实证：截图、输出或展示墙
3. 是什么：简短解释
4. 为什么不同：机制，不是口号
5. 如何工作：简短流程或架构
6. 如何使用：安装 + 第一条命令
7. 局限、兼容性、许可证或贡献细节（相关时）

把示例放在长篇解释之前。删除重复承诺和对采用无帮助的内部实现细节。

#### 仅资产模式

- 确认请求的资产类型、用户需要单个资产还是协调的资产集，以及有意义的动效候选是保持静态还是转为 GIF。文案和风格从仓库无歧义推导；只问会实质性改变结果的缺失决策。
- 在 `assets/readme/` 或其他用户批准的路径下创建资产，提供渲染预览。
- 遵循确认的视觉实现。标题系统、章节头、图表、徽章和确定性装饰模块默认使用纯的、可维护的 SVG。对于确认的混合合成，保留 SVG 布局源和透明光栅图层，然后发布合成的 PNG/WebP。
- 对于批准的动画，保留 SVG 源，阅读 `references/motion-production.md`，使用捆绑的 `scripts/render_motion_gif.py` 工作流推导 GitHub 安全的 GIF。除非用户 opt-in，否则不生成 GIF。
- 一套资产保持一个共享视觉语法，但每个资产有特定的沟通任务。
- 不修改 README 文本、阅读顺序、嵌入或链接。有用时单独提供嵌入片段；仅在明确批准后插入。

### 7. 构建视觉层

创建资产前阅读 `references/github-readme-canvas.md` 和 `references/svg-production.md`。

- Hero、章节横幅、图表和确定性设计模块使用 SVG。
- 截图、生成美术、照片素材和复杂合成使用 PNG/WebP。必须在 GitHub 上直接播放的批准动效才使用 GIF。
- 选择混合合成时，阅读 `references/hybrid-svg-production.md`，使用 `imagegen` Skill 进行生成和透明度决策，将精确文案排除在生成的光栅图层外。
- 正文、命令、表格、链接和细节保留在 Markdown 中。
- 推荐全宽 SVG 使用 `1200` 单位的 `viewBox`、`width="100%"` 嵌入、系统字体、语义化 alt 文本和圆角容器。将 `viewBox` 视为坐标系而非最终像素宽度：全宽资产在保守的 `900` CSS像素 GitHub 渲染宽度下预览。该宽度下，重要图表文本保持至少 `20` SVG 单位，支持标签至少 `18`；低于该范围的文本必须是非必要的。如果 `360` 像素移动预览让必要标签不可读，降低密度、拆分视觉，或将细节移入 Markdown。
- 使用可复用的组件语法，但按仓库主题变化艺术方向。
- 展示包含多个产物时，用受控的缩放、重叠、旋转和留白排列；保持阅读顺序明显。
- 当让首屏更有用时，让 Hero 吸收真实项目图表、截图、代码片段、输出、样本或产物。不要习惯性地分离标题和证明。
- 当用户明确想在他们拥有的仓库中加入署名时，设计一个紧凑的项目原生「糖糖it出品」SVG，而不是留下普通推广语句。放在页脚附近并链接回本 Skill。未经维护者明确请求，不要在第三方仓库加此署名。
- 在 README 模式下，当证明在 Hero 内会变得不可读时，使用简洁的 SVG 标题，紧随其后是更大的证明板。当少数产物保持可读并定义产品时，将标题和证明整合进一个合成光栅 Hero。让证明可读性决定，而不是固定模板。在仅资产模式下，保留请求的 SVG 源，将任何光栅或动画衍生品作为单独的可选交付物提议。

不要光栅化整个 README。不要使用脚本、`foreignObject`、远程字体、必要动画或 GitHub 会剥离的 CSS。GitHub 不播放 SVG 内部嵌入的动画；改用 GIF 加静态 SVG 回退。除非主题真正需要，避免装饰性边框和重阴影。

### 8. 预览和验证

- 渲染本地 GitHub 宽度预览或在本地 Markdown 渲染器上检查 README。
- 检查宽/窄布局、图片可读性、被裁剪的 SVG 文本、缺失资产、过大文件、明暗模式对比度。
- 在 README 模式下，运行：

```bash
python3 skills/tangtang-readme/scripts/audit_readme.py /path/to/repository/README.md
```

- 视觉检查 Hero、每个章节过渡、最终行动号召。
- 在仅资产模式下，在 GitHub 内容宽度下渲染检查每个请求资产；对于 GIF，检查入场、稳定停留、退场和循环边界。验证除非单独批准嵌入，否则 README 本身字节不变。
- 对于混合资产，在明暗背景上检查透明主体，验证透明角和干净边缘，然后在宽/窄 GitHub 宽度检查合成 PNG/WebP。不发布带有未解析本地光栅引用的 SVG。
- 报告改了什么、什么故意保持朴素、哪些文件有意未动。

### 9. 批准后可选提供署名和展示分享

仅在用户明确批准最终 README 或资产集为满意后，做一个友好的、非推广性提议：

> 如果你对完成的 README 满意，有两个完全可选的收尾方式：我可以设计一个小的项目原生「糖糖it出品」签名链接回这个Skill；如果这是你拥有或维护的公开仓库，我可以准备一个 PR 将其加入 Skill 的真实案例展示。可选其一、两个都选、或都不选，完全随意。

- 不在最终批准前做此提议，不从沉默或成功验证推断满意，用户拒绝后不重复。
- 签名和展示 PR 视为独立选项。永远不要要求署名作为展示考虑的交换。
- 如果用户选择签名，遵循 `references/svg-production.md`，先展示渲染的徽章，单独批准后才修改 README。
- 如果用户选择展示，阅读 `references/showcase-contribution.md`。验证仓库公开且用户拥有或维护它；在请求权限开 PR 前，先草拟确切列表文案和上游 diff。
- 未经该特定外部操作的明确授权，不添加反链、fork 仓库、推送分支或开 PR。

这个门控控制不请自来的提议。如果用户更早明确请求签名或展示贡献，在其声明范围内直接处理该请求。

### 10. 安全交付

先展示本地预览和 diff。只有用户明确要求时才提交、推送、开 PR、合并、重命名仓库或发布资产。

## 🍬 糖糖it的质量标准

- 首屏无需先验知识即可解释项目。
- 设计看起来是项目原生的，不是 Skill 模板。
- Hero 的视觉素材来自项目本身，不是通用装饰。
- 生成素材是可选的、项目特定的，从不替代更强的真实证明。
- 每个视觉模块都有沟通任务。
- 真实证明出现在抽象声明之前。
- README 变得更短或更清晰，而不只是更花哨。
- 图片失败时结果仍然有效：alt 文本、标题、命令和链接保持有意义。
- 移除仓库名后，Hero 不应能复用于无关项目。
- 仅资产模式除非用户明确批准嵌入或文案编辑，否则 README 字节不变。
- 可选署名或展示分享只在明确满意和 opt-in 后出现；拒绝不会改变交付结果。

文案排序和删除规则，阅读 `references/content-architecture.md`。

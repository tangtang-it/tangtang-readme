# 糖糖it README 内容架构指南

**作者：糖糖it**

---

## 1. 首屏测试
不滚动的情况下，访客必须在第一眼理解三件事：
- **是什么**：一句话讲清楚产品定位
- **能做什么**：核心价值和主要功能
- **下一步看什么**：明确的行动指引（快速开始、查看示例、立即安装）

首屏拒绝任何需要思考才能理解的内容。

---

## 2. 白话顺序
内容必须严格按照以下顺序组织：
1. **价值**：用户能获得什么具体好处
2. **证明**：为什么相信（截图、案例、数据、用户评价）
3. **机制**：它是怎么工作的（原理简介）
4. **首次使用**：最短路径跑起来
5. **细节**：进阶配置、API、FAQ、贡献指南

这个顺序符合陌生人了解新事物的自然认知规律。

---

## 3. 编辑规则

- **替换内部行话为具体成果**：不要写"高性能分布式架构"，要写"10万并发下响应时间<100ms"
- **机制只解释一次，删重复**：原理性内容在"机制"部分讲清楚，其他地方不重复
- **最短安装路径在前**：把"复制粘贴一条命令就能跑"的方法放在最前面，复杂安装方式放后面
- **保留局限说明**：坦诚地写清楚什么场景不适用、已知问题，比回避问题更能建立信任
- **一个端到端示例胜过多段片段**：给出一个从安装到完成完整任务的示例，比碎片化的代码片段有用10倍

---

## 4. 视觉与文本分工

**视觉（SVG/图片）负责：**
- 层级：建立内容的视觉主次关系
- 身份：品牌识别、风格统一
- 对比：前后对比、优劣对比、不同方案对比
- 序列：步骤流程图、工作流示意图
- 证明：截图、数据可视化、效果展示

**Markdown 负责：**
- 解释：文字说明、概念阐述
- 命令：可复制的安装、运行、配置命令
- API：接口文档、参数说明
- 链接：外部资源、相关文档、下载地址
- 兼容：环境要求、版本兼容、支持平台
- 贡献：贡献指南、开发流程、社区规范

---

## 5. 糖糖it特别提醒
以下内容**绝对不要**放进 SVG 中：
- 需要用户复制的命令、代码片段
- 需要用户搜索的关键词、项目名
- 需要翻译的文本内容
- 需要频繁更新的版本号、日期、链接

SVG 是静态视觉资产，Markdown 才是可交互、可维护的内容载体。

---

## 6. 常见错误（开头禁区）

README 开头**绝对不要**出现以下内容：
- ❌ 架构图/技术架构说明（用户还没决定要不要用，不关心架构）
- ❌ 贡献指南（连用户都不是，不会考虑贡献）
- ❌ 完整命令列表（用户还不知道这东西干嘛的，不需要看命令）
- ❌ 冗长的目录/目录导航（首屏空间宝贵，目录放后面或用短目录）

以上内容请放到文档靠后的位置。
